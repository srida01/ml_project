---

## 1. Project identity

**Working title:** Multi-Stage ML-Powered Intrusion Detection Engine for Known and Potentially Novel Network Attacks

**Domain:** Cybersecurity / network intrusion detection / machine learning.

**One-sentence goal:** Build a reproducible intrusion detection engine that filters suspicious network flows, classifies known attack categories using stacking, models the time evolution of traffic with a Hidden Markov Model (HMM), and independently detects anomalous traffic using an autoencoder.

### 1.1 Problem statement

Signature-based intrusion detection depends heavily on predefined attack patterns and can miss previously unseen behavior. A single supervised ML classifier can also struggle with imbalanced attack classes, traffic variation, false alarms, and unfamiliar attacks. Network flow observations have temporal dependencies that ordinary row-wise classifiers do not capture. This project explores a **multi-component detection architecture** to address these limitations while honestly quantifying its trade-offs.

### 1.2 Research questions

1. Can a high-recall SVM distinguish suspicious flows from benign traffic without an unacceptable false-positive rate?
2. Can stacked Random Forest, XGBoost, and Logistic Regression models improve known-attack classification compared with individual models?
3. Does temporal modeling via HMM add meaningful value for session/sequence-level inference and next-state prediction?
4. Can a benign-trained autoencoder flag distribution shifts or withheld attack families that supervised models have not seen?
5. Does combining supervised and unsupervised evidence improve detection metrics under realistic leakage-resistant evaluation?
6. What are the accuracy, recall, latency, memory, and complexity trade-offs of the full architecture?

### 1.3 What this project **is** and **is not**

**It is:** a testable ML research prototype using labeled flow records, saved models, repeatable experiment scripts, a command-line inference entry point, a FastAPI backend, and a Streamlit frontend.

**It is not initially:** a live packet sniffer, network firewall, production SIEM integration, or a security product proven to detect genuinely new threats. The dashboard and REST API provide local demonstrations and file-based analysis, not proof of production readiness.

**Out of scope unless explicitly added later:** cloud deployment, automatic IP blocking, kernel packet capture, online learning, authentication infrastructure for public hosting.

## 3. Dataset: CICIDS2017

### 3.1 Dataset description

CICIDS2017 contains benign and simulated attack traffic captured across multiple days and commonly released as flow-based feature CSV files generated by CICFlowMeter. The actual files/features/label spelling vary by distribution. **Do not assume the exact number of columns, rows, or attack classes without inspecting the downloaded files.**

Common attack labels/families include:

- BENIGN
- Bot
- DDoS
- DoS GoldenEye, DoS Hulk, DoS Slowhttptest, DoS slowloris, Heartbleed
- FTP-Patator, SSH-Patator
- PortScan
- Web Attack – Brute Force, Web Attack – XSS, Web Attack – Sql Injection
- Infiltration

This is an **illustrative list**. The pipeline must inventory the actual labels in the local dataset and map them in a versioned file.

### 3.2 Data sources and integrity

Document:

- Original download source/URL and download date.
- Exact list of raw files, sizes, checksums (SHA-256).
- CSV encoding, delimiter, column names, and duplicate columns.
- Original label distribution **per source file/day**.
- Missing files or corrupted records.
- Any corrections applied to the label/feature schema.

Keep `data/raw/` immutable. Never write cleaned files over raw files.

### 3.3 Target variables

Maintain three distinct concepts:

- `raw_label`: original label from data, preserved for audit.
- `binary_label`: `0` for benign, `1` for attack.
- `multiclass_label`: configurable attack label or attack-family mapping.

Store explicit mapping in `configs/label_map.yaml`. Attack names must not be inferred from input features at inference time. The model’s target space must be fixed **from the training set**; unseen test labels require explicit open-set evaluation rules.

### 3.4 Metadata vs predictive features

Keep the following outside the feature matrix when available:

- `source_file`, capture day, original row index / stable `flow_id`.
- Timestamps, source/destination addresses and ports, protocols, and flow/session IDs as needed for grouping/sequences.
- All labels, train/validation/test assignments, evaluation-only attack-family identifiers.

**Avoid learning capture identifiers or timestamps as shortcuts.** Some metadata may be useful for grouping and temporal modeling, but must not automatically become classifier features.

## 4. System architecture

```text
                          INPUT: CICIDS2017 FLOW RECORDS
                                       |
                 schema checks + deterministic cleaning
                                       |
                        saved feature transformations
                                       |
                    +------------------+------------------+
                    |                                     |
        SUPERVISED KNOWN-ATTACK BRANCH          INDEPENDENT ANOMALY BRANCH
                    |                                     |
       Stage 1: binary high-recall SVM        Stage 4: benign-trained
         BENIGN / SUSPICIOUS                    AUTOENCODER
                    |                                     |
         suspicious flows only                 reconstruction error
                    |                                     |
       Stage 2: stacked multiclass                anomaly flag
       RF + XGBoost + Logistic Regression              |
                    |                                     |
         known attack family + score                     |
                    +------------------+------------------+
                                       |
                        explicit decision-fusion rules
                                       |
                         final flow-level alert/result
                                       |
                       group/order flows into sequences
                                       |
                         Stage 3: HMM temporal model
                                       |
               smoothed state estimates / next-state forecast
                                       |
                         reports + batch CLI outputs
```

**Conceptual ordering note:** “Stage 3” and “Stage 4” are labels for components, not a required order of execution. The autoencoder runs **in parallel** with the supervised branch. The HMM consumes ordered sequences, not isolated shuffled rows. HMM-derived estimates should be treated as a temporal enrichment unless a separately validated fusion experiment shows they improve alerts.

### 4.1 Stage 1 — suspicious traffic filter

**Input:** leakage-safe preprocessed numeric flow features.  
**Model:** binary SVM, preferably RBF/kernel SVM as the research target.  
**Output:** suspicion score, decision threshold, benign/suspicious decision.

Optimization emphasis: **high attack recall**, with benign false-positive rate and compute cost also reported. Tune threshold using validation data; never tune it on the final test set.

**Scalability reality:** exact nonlinear kernel SVM training scales poorly to millions of flows. Plan a stratified, group-aware sample for kernel-SVM experiments; compare against an approximate nonlinear alternative (e.g., RBFSampler/Nystroem + linear classifier) or linear SVM if exact kernel fitting is infeasible. Report any substitutions rather than silently changing the specified design.

### 4.2 Stage 2 — known-attack multiclass classification

Train on the appropriate **training attack examples**, with a clearly documented policy for any benign class. Recommended design:

- The SVM gates traffic; **only suspicious/gated traffic** is passed to the known-attack classifier at inference.
- The multiclass classifier predicts **known attack families** among attacks represented in training.
- Train its base models using labeled attack-training examples; avoid accidentally teaching a model that all gated benign false positives are attacks without accounting for that in final evaluation.
- Evaluate the classifier twice: (a) on oracle-labeled attack rows to assess classification skill, and (b) **end-to-end after the SVM gate** to measure propagated SVM misses and false positives.

Base learners:

1. Random Forest: bagging and nonlinear interactions.
2. XGBoost: boosted trees and minority-class discrimination.
3. Logistic Regression: a simpler, interpretable baseline.

**Stacking mechanism:** Create **out-of-fold (OOF)** class probabilities from base models on training data, using group-aware folds where possible. Train a regularized Logistic Regression meta-learner on OOF predictions. Refit base models on the full training subset. Use validation for threshold/calibration/model selection; use test only at the end. Never train the meta-model on in-sample probabilities from models fitted to the same rows.

### 4.3 Stage 3 — temporal behavior / HMM

**Objective:** model temporal changes in inferred attack/traffic states and estimate the next likely state.

Requirements:

- Define a defensible sequence identity (e.g., bidirectional 5-tuple/session when metadata supports it, or an explicitly described proxy grouping).
- Sort events by timestamps within each group; prevent mixing different capture days or unrelated hosts.
- Document the timestamp resolution and whether flow start/end times are usable.
- Avoid sequences of length one for temporal claims; quantify how many valid sequences exist.
- Split sequences by independent groups **before** learning HMM parameters.
- Choose emissions explicitly: categorical/discrete labels/scores after binning, or numeric emissions (Gaussian HMM) from low-dimensional features.
- Fit HMM only on training sequences; select state count using validation and likelihood/stability checks.
- Do **not** use ground-truth labels as emissions during test-time inference. If predicted class probabilities are emissions, generate leakage-safe OOF predictions for HMM training and normal model predictions at validation/test.
- Estimate next-observation/next-state distribution via current filtered state distribution and learned transition matrix.

**Important limitation:** CICIDS2017 CSVs may not contain robust session identifiers or sufficiently granular usable chronology in all distributions. If so, describe HMM results as exploratory, do **not** claim genuine session next-attack prediction without evidence, and use a carefully scoped pseudo-sequence experiment or obtain richer source metadata.

### 4.4 Stage 4 — anomaly detection / potential unknown attacks

**Model:** neural autoencoder trained exclusively on **benign training** examples after feature preprocessing fitted only on training data.

Suggested initial design:

- Input: scaled numeric features.
- Encoder: `input_dim -> 128 -> 64 -> 16` (adjust after examining feature count).
- Decoder: `16 -> 64 -> 128 -> input_dim`.
- Activation: ReLU in hidden layers; output/loss consistent with feature scaling.
- Loss: MSE or robust reconstruction loss; use train/validation separation and early stopping.
- Score: per-flow reconstruction error; larger generally means more anomalous.
- Threshold: choose from benign validation distribution (e.g., target 1% benign FPR) or an explicit validation operating-point objective.

**Interpretation:** an anomalous flow is **not** proof of an unknown malicious attack. It is suspicious/out-of-distribution relative to learned benign traffic. Report benign false positives and performance on withheld attack families. Never train the autoencoder on benign rows from validation/test sets.

### 4.5 Decision fusion

Start with a transparent, auditable rule-based policy, and compare alternatives on validation data:

| SVM suspicious? | AE anomaly? | Known-class output | Initial action |
|---|---|---|---|
| No | No | Not run | Benign / low risk |
| Yes | No | Known attack with adequate confidence | Known-attack alert |
| No | Yes | Not run | Anomaly alert / review |
| Yes | Yes | Known attack with adequate confidence | High-priority known-attack alert |
| Yes | Yes/No | Low confidence or uncertain | Suspicious / unclassified alert |

- **Do not** label a case “unknown attack” solely because AE scored it anomalous.
- Establish validation-based confidence/alert thresholds and document costs.
- Preserve stage-level outputs to enable forensic inspection.
- For HMM, first output temporal context separately; later run an ablation to test whether any temporal alert adjustment actually helps.

- Log sample sizes, wall time, peak memory, device, and exact hyperparameters.

## 7. Complete implementation phases

The numbered phases below are the **single source of truth**. Older work/checkpoints do not count.

### PHASE 0 — repository + data audit + cleaning

**Goal:** obtain trustworthy, standardized flow records without premature ML preprocessing.

**Tasks:**

- [ ] Create directory structure, virtual environment, `.gitignore`, requirements, and configs.
- [ ] Download/locate CICIDS2017 raw CSV files; preserve originals.
- [ ] Record files, byte sizes, SHA-256, schemas, row counts, label counts.
- [ ] Normalize feature names and resolve leading/trailing whitespace.
- [ ] Detect duplicate column names and conflicting field meanings.
- [ ] Identify string/non-numeric artifacts in numeric columns.
- [ ] Replace `+inf/-inf` with missing values and document rates.
- [ ] Identify missing values per feature/file/label; specify cleaning policy.
- [ ] Handle exact duplicated records with **auditable policy**; avoid deleting meaningful repeated events blindly (duplicates may encode repeated flows).
- [ ] Identify constant and near-constant columns; record candidates for later removal.
- [ ] Check impossible physical values (negative durations, inconsistent rates, outliers) and document handling rather than blindly deleting attacks.
- [ ] Preserve raw labels, source file, row index, timestamp/group metadata when available.
- [ ] Add binary labels and versioned multiclass mapping.
- [ ] Validate row counts before/after cleaning and distribution shifts.
- [ ] Write cleaned dataset in Parquet, in chunks where necessary.
- [ ] Export `data_quality_report.json` and class distributions by capture file/day.
- [ ] Test deterministic reruns and sample clean rows manually.

**Output:** `data/interim/cicids2017_cleaned.parquet` (or partitioned Parquet dataset), cleaning log, manifest, audit report.

**Exit gate:** no silent dropped rows, duplicate columns, undocumented label mapping, or unresolved datatype problems.

**NOT Phase 0:** split finalization, scaling, SMOTE, feature selection, full model training, HMM fitting, autoencoder training.

### PHASE 1 — leakage-resistant splits and preprocessing

**Goal:** make reliable training/evaluation partitions and reusable transformations.

**Tasks:**

- [ ] Decide closed-set benchmark vs open-set/withheld-family evaluation **before modeling**.
- [ ] Inspect feature/label overlap across capture days; document leakage risks.
- [ ] Choose splitting unit (capture day, source-file group, temporal block, host/session where possible).
- [ ] Prefer realistic blocked/group holdouts when viable; explicitly report class coverage trade-offs.
- [ ] If random stratified splitting is used as a secondary benchmark, label it an optimistic IID setting.
- [ ] Keep training, validation, final test groups disjoint to the extent permitted by the dataset.
- [ ] Fit deduplication and leakage audits across train/validation/test; detect exact feature-row overlaps.
- [ ] Exclude target, raw labels, capture identifiers, and eval-only metadata from predictive features.
- [ ] Fit imputer on **train only**; transform val/test with same imputer.
- [ ] Fit scaler on **train only** for SVM/LR/AE (e.g., StandardScaler/RobustScaler).
- [ ] Use appropriately handled numeric inputs for trees (a shared feature schema is required; scaling may be shared for consistency).
- [ ] Remove train-identified constant features and optionally use feature selection fitted on train only.
- [ ] Store feature order and dtype contract.
- [ ] Quantify data imbalance, decide class weights/resampling **inside training only**.
- [ ] Save split manifest, trained preprocessing artifacts, hashes, and seeds.

**Recommended evaluation protocols:**

1. **Closed-set:** only attack families present in model training; strict group-aware split where feasible.
2. **Open-set:** withhold one or more entire attack families from **supervised model training and tuning**, then assess detection as novel/anomalous in a separate evaluation. Ensure held-out examples are not used to tune anomaly thresholds or meta-models.
3. **Optional IID sanity check:** random stratified split for comparison only, never claim it replicates future real traffic.

**Exit gate:** no feature/target leakage; clear split rationale and frozen test holdout.

### PHASE 2 — baseline models and metric infrastructure

**Tasks:**

- [ ] Write reusable metrics, plotting, timing, logging, and config loading.
- [ ] Create simple majority/stratified baselines and logistic/tree binary baselines.
- [ ] Evaluate per-class support, precision, recall, F1, macro-F1, weighted-F1, balanced accuracy.
- [ ] Include PR-AUC and ROC-AUC when defined and probabilities/scores are available.
- [ ] Save confusion matrices, threshold curves, and probability-calibration checks.
- [ ] Record runtime and peak RAM of training and inference.

**Exit gate:** metrics match independent tests and use the appropriate population/denominators.

### PHASE 3 — binary SVM filter

**Tasks:**

- [ ] Train baseline linear SVM or linear classifier to estimate feasibility.

- [ ] Tune `C`, `gamma`, sampling policy, and class weights using train/validation only.

- [ ] Quantify full-set and per-attack-family false negatives.
- [ ] Save best model, threshold, preprocessing dependency, and model card.

### PHASE 4 — stacked multiclass ensemble

**Tasks:**

- [ ] Train meta-learner on OOF probabilities only (plus documented optional features).

### PHASE 6 — HMM temporal analysis

**Tasks:**

- [ ] Audit usable timestamp, 5-tuple/session/host metadata.
- [ ] Define actual sequence unit; explain any lack of genuine session info.

- [ ] Train HMM candidates; tune hidden state count and regularization/stability.
- [ ] Estimate transition matrix and state occupancy.
- [ ] Report filtering accuracy or predictive log-likelihood; avoid using future observations for purported real-time predictions.
- [ ] Predict next hidden/observed state distribution using past/current data only.
- [ ] Compare against majority state and first-order empirical Markov baseline.
- [ ] Save HMM, grouping rules, emission transforms, state interpretation.

**Exit gate:** valid time order, reproducible sequences, no future information leakage, and clearly scoped interpretation.

## 8. Essential ML pipeline (end-to-end)

```text
Define problem + target labels
    -> acquire and document data
    -> inspect/audit quality
    -> clean raw flow rows
    -> construct robust splits
    -> fit preprocessing on train only
    -> establish baselines
    -> train and tune SVM
    -> train OOF stacked classifier
    -> train benign AE in parallel
    -> build temporal sequences and train HMM
    -> calibrate scores / set thresholds on validation
    -> combine outputs in decision engine
    -> final frozen test evaluation
    -> save artifacts, charts, code and CLI
```

**Do not:** scale before the split; select features using all data; SMOTE before the split; tune thresholds on the test set; fit stacker on in-sample base predictions; train an HMM on shuffled rows; evaluate unknown attacks that were used to tune the unknown detection threshold.

## 9. Metrics and acceptance criteria

### 9.1 Binary intrusion detection

Given TP/FP/TN/FN for **attack = positive**:

- Precision = TP / (TP + FP)
- Recall / TPR = TP / (TP + FN)
- Specificity / TNR = TN / (TN + FP)
- FPR = FP / (FP + TN)
- F1 = 2 × Precision × Recall / (Precision + Recall)
- PR-AUC and ROC-AUC across thresholds (when defined)
- Alert volume per 1,000 benign flows (operational perspective)

### 9.2 Known-attack classification

Macro-F1, weighted-F1, per-class precision/recall/F1, support, confusion matrix, and (where appropriate) top-2 accuracy. Separate **attack-only oracle** and **full pipeline** metrics.

### 9.3 Anomaly / open-set detection

- Benign validation FPR at chosen threshold.
- Known-attack TPR.
- **Withheld-family** TPR and detection trade-off at fixed benign FPR.
- Score histograms/PR curves; class/family breakdown.
- Optional AUROC for anomaly vs benign, with cautious interpretation.

### 9.4 Temporal modeling

- Percentage of rows that can be formed into usable sequences.
- Number of independent sequences and length distribution.
- Held-out sequence log-likelihood/perplexity where valid.
- Next-step state/observation accuracy or negative log-likelihood (define ground-truth target).
- Difference vs majority-state and empirical Markov baselines.

### 9.5 Efficiency

Training time, inference ms/flow (batch sizes specified), flows/second, peak RSS RAM, GPU memory if applicable, disk model sizes, and environment specs.

### 9.6 Success criteria

**Do not invent target performance figures.** Set numeric project acceptance targets after basic data audit and baselines, using validation trade-offs. Minimum non-negotiable success criteria are: (1) leakage audits pass; (2) every stage executes reproducibly; (3) final metrics are computed on untouched test data; (4) novelty claims are tied to withheld-family tests; (5) code, configs and artifacts support batch inference.

## 10. Important design decisions to settle early

| Decision | Recommended initial default | Why it matters |
|---|---|---|
| Unit of input | CICFlowMeter-style network flow row | Defines features and inference schema |
| Binary target | Benign=0; all attacks=1 | SVM task |
| Multiclass target | Versioned attack-family map | Reduces sparse subclasses when justified |
| Split | Group/day-aware primary, IID secondary | Reduces misleading leakage |
| Preprocessing | Train-fitted imputer + scaler | SVM/LR/AE need stable distributions |
| Imbalance | Class weights first; cautious resampling | Avoid split contamination |
| SVM | RBF on feasible subset, approximate alternative | Kernel scaling limit |
| Stacking | OOF probability features + LR meta model | Prevents stack overfitting/leakage |
| AE training | Benign-only train split | Meaningful anomaly baseline |
| AE threshold | Benign validation quantile | Controlled normal FPR |
| HMM emissions | Predictions/compact numeric features, not truth | Usable during actual inference |
| HMM sequences | Genuine chronology where supported | Valid temporal claims |
| Fusion | Explicit rules before learned fusion | Auditability |
| Inference | Batch CLI | Matches scope; no web app required |
| Evaluation | Closed-set + withheld-family | Known/novel threat distinction |

### 11.2 Required prediction fields

A recommended batch result schema:

```text
flow_id
svm_score, svm_suspicious
known_attack_label, known_attack_confidence
anomaly_score, anomaly_flag
final_alert_label, final_alert_level
sequence_id, hmm_current_state, hmm_next_state, hmm_next_state_confidence
model_version, inference_timestamp
```

Missing temporal context must be represented as null/not-applicable, not a fabricated prediction. Never include `true_label` in production-like inference output unless an explicitly marked evaluation mode requests it.

### 11.3 Test checklist

- [ ] Binary/multiclass mapping returns expected classes.
- [ ] Cleaning handles NaN/inf/invalid numeric strings deterministically.
- [ ] Label columns never appear among training features.
- [ ] Train-fitted imputer/scaler never refits on val/test.
- [ ] Split groups are disjoint; row/feature overlap report is generated.
- [ ] OOF meta-features never come from base models fitted on the same OOF row.
- [ ] All class-probability arrays use the same class order.
- [ ] AE training loader contains benign labels only.
- [ ] HMM sequence timestamps are monotonic within each sequence.
- [ ] HMM test-time features do not use true test labels or future observations.
- [ ] Fusion covers disagreeing SVM/AE outputs and uncertain classifier output.
- [ ] Saved artifacts can be loaded in a fresh process.
- [ ] CLI returns stable predictions on fixture inputs and rejects schema violations.

## 13. Known risks and mitigations

| Risk | Mitigation |
|---|---|
| Data leakage due to capture day/identifiers | Remove shortcuts; group-aware splits; report overlap |
| Extreme class imbalance | Per-class metrics, class weights, careful train-only resampling |
| SVM time/RAM explosion | Feasible subset; approximate SVM alternative; profile |
| Preprocessing RAM crash | Chunked file reads, Parquet, float32, no needless copies |
| Stack overfitting | OOF meta-features, group-aware CV, held-out tests |
| Error propagation from SVM gate | End-to-end recall; parallel AE safety net |
| AE false positives | Validation FPR budgeting, calibration, threshold stability |
| “Unknown” attack overclaim | Say potential novelty/anomaly; use withheld-family protocol |
| No reliable session information | Audit temporal fields; constrain HMM claim or revise method |
| HMM uses future/test labels | Strict causal inference and inference-available emissions |
| Rare family absent from training days | Explicitly separate closed/open-set evaluation populations |
| Synthetic/lab data ≠ production | Discuss domain shift; do not assert real-world efficacy |
| Different CSV feature schema | Central schema mapping and validation |
| Models produce incompatible labels | Canonical label index and output-contract tests |

## 18. FastAPI backend — complete implementation specification

**Purpose:** expose the saved, evaluated inference engine through a local REST API. The backend does *not* retrain models on requests; all training remains in offline scripts. Only trusted, versioned model artifacts are loaded at server startup.

### 18.1 Request lifecycle and architecture

```text
CSV upload or single flow → Streamlit client / HTTP client
                          ↓
                     FastAPI routes
                          ↓
           validate input schema and resource limits
                          ↓
                shared ids.pipeline.predict
                          ↓
           fitted preprocessing and saved models
             ┌────────┴─────────┐
         SVM → stacking     independent AE
             └────────┬─────────┘
                      ↓
        HMM temporal inference (only with valid sequence context)
                      ↓
             fusion + alert decision
                      ↓
        typed JSON response / downloadable CSV
```

- **One inference implementation:** `src/ids/pipeline/predict.py` is called by the CLI and API. There must be no duplicated feature engineering or separate thresholds inside the API/UI.
- **Startup:** validate artifact manifest (feature ordering, label mapping, model versions, thresholds), load trusted files once in FastAPI lifespan, set models to eval/inference mode, fail startup with clear logs if incompatible.
- **Inputs:** feature vectors/CSV must match the training-time inference schema, excluding `Label`, splits, attack targets, and privileged metadata. Additional sequence metadata may be accepted separately where required by the HMM.
- **Output:** return labels, relevant probabilities/scores, anomaly flag, fusion decision and version info. State when temporal inference is unavailable instead of silently inventing sequence context.

### 18.2 Required HTTP endpoints

| Method/path | Behavior | Core checks |
| --- | --- | --- |
| `GET /health` | readiness/liveness and artifact-loaded state | health can be non-ready on load error |
| `GET /model-info` | public-safe artifact version, supported labels and required input fields | no internal paths/secrets |
| `POST /predict` | predict a single validated flow | required numeric fields, finite values, correct feature order |
| `POST /predict-batch` | predict validated list of flows as JSON | configurable row cap and request size |
| `POST /predict-file` | upload a CSV for batch inference | extension/content validation, size/row cap, streaming/bounded parser |

**Illustrative JSON request:**

```json
{
  "flow": {
    "Destination Port": 443,
    "Flow Duration": 2500
  }
}
```

The example is *not* a complete valid CICIDS2017 input; the endpoint will require the full set of features actually selected by the frozen training schema. Generate a real sample request from a schema-valid held-out feature row.

**Illustrative response contract:**

```json
{
  "prediction": {
    "binary_label": "suspicious",
    "attack_label": "DoS",
    "attack_probability": 0.91,
    "anomaly_score": 0.27,
    "anomaly_flag": true,
    "temporal_status": "unavailable_no_sequence",
    "next_state_prediction": null,
    "final_alert": "known_attack_suspected"
  },
  "model_version": "example-version"
}
```

Values and names here are **examples only**, not measured predictions. Actual response schema must support `null` when probabilities or temporal outputs cannot be provided, include calibrated/un-calibrated score definitions, and distinguish anomaly flags from confirmed zero-day attacks. The binary class and final decision may differ because anomaly evidence runs independently.

### 18.3 Engineering tasks

- [ ] Define Pydantic schemas in `src/ids/api/schemas.py`, including helpful 4xx errors for missing, unexpected, malformed or non-finite fields.
- [ ] Build `create_app()` / FastAPI lifespan in `src/ids/api/main.py`; use a single `InferenceService` in `service.py`.
- [ ] Implement readiness, versioning, error messages, JSON single and batch routes and bounded CSV-upload route.
- [ ] Add batch-size, file-size, execution timeout and concurrency/resource protections; handle large files in bounded chunks.
- [ ] Disallow arbitrary user-uploaded pickle/model files; never log raw sensitive records by default.
- [ ] Document request schema via autogenerated `/docs` and `/openapi.json`.
- [ ] Test malformed inputs, missing models, empty CSV, duplicate columns, unsupported labels/features, large requests, and safe error messages.
- [ ] Check CLI/API parity with a deterministic sample. Measure warm/cold inference latency.
- [ ] Use local-only binding by default; if deployed externally later, add authentication, TLS, rate-limits, CORS allowlist, monitoring, and privacy controls.

**Local command (after code and dependencies exist):**

```bash
uvicorn ids.api.main:app --app-dir src --host 127.0.0.1 --port 8000 --reload
```

### 18.4 Boundaries and tricky cases

- The HMM cannot infer meaningful next-state predictions from one unordered row. For `/predict`, return `temporal_status=unavailable_no_sequence` unless a validated sequence is explicitly supplied. For batches, require sequence identity and chronological ordering; otherwise treat them as unrelated flows.
- Fused decisions must be versioned and based on validation-frozen thresholds, not recomputed from test data or adjusted interactively by users.
- Serving a very large exact-kernel SVM may exceed local RAM/latency budgets; benchmark before deciding if the API can meet interactive speed goals.
- Uploaded CSV data is potentially sensitive and untrusted; do not commit uploads, predictions, or user traffic to Git.

## 19. Streamlit dashboard — complete implementation specification

**Purpose:** explain and demonstrate end-to-end predictions through an interactive local UI. Streamlit is a thin API client: the trained ML pipeline belongs to the shared `ids` package and is executed inside FastAPI.

### 19.1 Proposed dashboard layout

1. **Home / Overview:** project objective, architecture graphic, supported attack classes, model manifest version, and backend status.
2. **Predict a Flow:** schema-driven numeric input form (or a valid sample record), call `/predict`, display classification, anomaly warning, confidence interpretation and temporal availability.
3. **Batch Upload:** CSV uploader and preview; show required column list and validation messages; submit to `/predict-file` or chunked `/predict-batch`.
4. **Results:** table with flow IDs and predictions; class distribution plot, alerts by severity (if defined), anomaly-score histogram, known vs anomaly-only alerts and filters.
5. **Temporal Analysis:** where sequence metadata exists, ordered per-session attack-state plots and next-state predictions; explicit “not available” message otherwise.
6. **Evaluation / About:** offline benchmark metrics from finalized immutable report files, dataset disclaimer, leakage-safe protocol and limitations; never mistake uploaded unlabeled flow predictions for ground-truth accuracy.
7. **Export:** download results CSV with predictions, score/threshold definitions and model version; remove unnecessary personal/sensitive fields by default.

### 19.2 UI workflow and behavior

```text
Open Streamlit → show backend connectivity/version
   ├─ Single-record form → validate → POST /predict → result cards
   └─ CSV upload → preview/check schema → POST /predict-file
```
